# First Google Play Launch

Use when preparing the first listing/release for an existing Android product. This mode creates the
initial baseline; it does not invent an old store revision or choose None because there is no history.
Reuse an existing Console app, test-track bundle, approved source and verified setup wherever possible.

## Establish Initial Decisions

Resolve the target developer account, package, app name/type, default store language, download pricing
model, contact/privacy sources, intended countries and track from accepted product decisions. App UI
languages, listing locales and countries are separate choices. Inspect current Console requirements,
account eligibility, applicable testing/access requirements and current SDK/policy requirements before
promising a production-ready submission. Do not hardcode a tester count, elapsed waiting period or SDK
deadline in the reusable workflow.

Preparing a first launch covers research, assets, verification and draft preparation. Create a Console
app only when the user's request covers creating that app entry and its identity is resolved. Initial
pricing, country scope, signing enrollment and legal attestations require the corresponding accepted
decisions/authority; reuse them when present. Finish independent work before asking about a missing
decision. Do not guess declarations or accept new terms simply to advance a wizard.

Keep keys in their existing provider. If no release signing setup exists, prepare the configuration plan
and resolve its ownership before creating keys or accepting enrollment. A factory-generated legal page
describes the initial shell; verify the implemented app and SDK data flows before using it for launch.

## Prepare The Initial Listing And Review Inputs

Use [store-refresh.md](store-refresh.md) to establish the initial value proposition, screenshot story,
real product captures, editable sources, localized text and asset coverage. Research current Play asset
guidance and relevant visual references when needed for this first design. Deliver a concrete owner
review before saving new design/copy to Console. Reuse approval of unchanged source material.

Inspect the app dashboard and App content surfaces. Prepare applicable privacy/data safety, ads, app
access, target audience/content rating, permission and category-specific declarations from the actual
product. Verify reviewer access instructions when required without exposing private user data. Confirm
the privacy URL is publicly reachable and describes current behavior. Resolve missing attestations with
the owner; a default answer is not evidence.

Run [release preparation](release-preparation.md) for the verified AAB, notes, build/device gates and
authorized uploads. Save approved initial listing/declaration fields within the agreed scope and read
back the actual persisted values, languages, asset order, track and outstanding dashboard checks.
Store listings can be shared across tracks; test-release preparation is not an isolated store sandbox.

## Stop At The Correct State

Stop before final review submission, publication or tester distribution on every track by default.
If production access or a testing prerequisite is incomplete, report that exact gap while completing
the available draft. Do not change tracks or publish a test build to work around missing authority.

Record the first prepared binary/store identities and separate saved/submitted/live observations using
[project-context.md](project-context.md). Only a verified live release establishes the live baseline
used by later updates. Hand off the exact Console destination, saved content and owner action.
