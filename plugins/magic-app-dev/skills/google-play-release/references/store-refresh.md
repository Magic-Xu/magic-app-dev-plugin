# Refresh Store Content When The Assessment Calls For It

For Partial, keep accurate content and existing composition; update the affected claims, scenes or
translations. For Full, rework the relevant store story. A store-only request can use either path without
a binary release. Store changes are shared beyond one testing track, so do not assume a draft/test AAB
makes corresponding public marketing accurate for the current production audience.

## Design From Verified Product Behavior

Build a small fact-to-claim map from the actual product: benefit, available UI/action, source evidence,
free/paid availability and candidate screenshot. Honor explicit app marketing exclusions. Distinguish
on-device editing from ads, purchases, analytics or other network activity; a capture with ads hidden
does not justify an ad-free claim. Explain paid boundaries briefly where relevant without making price
promotions the visual story. Never describe paid-only features as available free to everyone.

Use maintained brand and render sources. For a redesign, research current official Play guidance and
relevant high-quality app listings; cite sources and dates in the review context. Verify any “featured”
or award claim rather than inferring it from an attractive listing. Borrow communication patterns, not
competitor artwork, layouts, app UI or unsupported capabilities. Research is conditional, not a routine
release prerequisite.

Prefer a readable sequence showing the core benefit and real result first, followed by distinct useful
capabilities and evidence. Choose the number of images for the story and device type; do not enforce a
fixed six-screen template. Keep one clear point per frame, readable type at store scale, consistent visual
hierarchy and an accurate relationship between headline and captured UI. Demonstrate outcomes without
inventing controls or removing commercially meaningful output watermarks.

## Capture And Produce Reviewable Assets

- Inspect available devices and choose the intended target. Use the accepted build or a capture build
  whose demonstrated behavior matches it; record its identity. Follow the project's install/data policy.
  Do not uninstall an existing app or clear user data merely to get a clean screenshot without authority.
- Apply the app's approved screenshot setup, including its developer ad-hiding switch when configured.
  This is separate from release QA and release build configuration. Use fictional demo data and app-owned
  fixtures. Record and restore temporary language/font/device settings after capture where changed.
- Capture actual app screens and outputs. Crop/frame/layout them using established editable sources and
  tools; preserve visible behavior. Use image generation/editing tools according to their instructions
  for appropriate demo/illustration assets, never to fabricate app UI or recognition results. Track asset
  provenance for any declarations the current Console asks for.
- Create a compact review page/contact sheet with readable full-size images, changed descriptions and
  old/new comparison where it helps. Start with the project's agreed review languages (for example a
  Chinese/English comparison), and show the proposed order, locale coverage and factual changes.
- Obtain owner approval of changed design/copy before Console writes. Continue independent release
  preparation while waiting. Reuse accepted source files; substantive later changes require review.

## Localize And Validate

Complete the agreed locale matrix after design approval. Reuse brand terms and accurate translations,
checking overflow, line breaks, RTL, readability, embedded UI language, demo data and text-image agreement.
Do not silently reuse English art for every locale unless the project's approved fallback map permits it.
Do not equate translated store text with an app UI language the product does not support.

Inspect all changed images, including at thumbnail scale. Run existing character/image validators and
render scripts. Verify dimensions, format/alpha, size, screenshot count/order, missing assets and source
provenance against current Play requirements for the actual device category. Distinguish mandatory
requirements from recommendation eligibility. Maintain appropriate accessibility text and accurately
answer any AI/media declarations shown by Console.

Use one canonical copy source per locale/field and one editable visual source; generated imports, previews
and ZIPs derive from them. Keep design sources, publication inputs and disposable output in their proper
project locations. A Console translation/import feature does not prove that approved copy was preserved.

## Save And Read Back

Inventory default/custom listings and current text/image inheritance before writing. Replace only the
approved scope; confirm the actively selected locale before each edit. Verify final effective assets,
including inherited ones, so a locale override does not leave obsolete images visible.

After saving, reload/reopen each affected locale and compare title, short/full description, screenshot
count/order/content, feature graphic and relevant alt text/declarations with the intended sources. Also
check dependent locales affected by a default asset replacement. Preserve unrelated videos, icons,
device categories, custom listings and experiments unless the approved update includes them.

Account for publication timing when new claims depend on the candidate binary. Review current Console
pending state and the project's publication policy; if the store and binary could become live in an
incompatible order, explain the concrete sequencing needed. Do not change managed publishing or submit
early to solve it. Finish at the owner's submission/publication boundary with the necessary ordering clear.
