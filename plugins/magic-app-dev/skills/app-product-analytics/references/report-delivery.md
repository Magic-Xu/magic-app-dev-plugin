# Analysis Report Delivery

Use for completed product or stability analyses based on live or supplied app data. Conceptual
explanations do not create a report. The requested analysis owns one report; a stability contribution
to product analytics joins that report instead of creating a second document.

## Choose The Destination

Follow the explicit user deliverable first, then the project's established reporting destination. In
the absence of either, retain this plugin's default of a Lark document. Resolve delivery capability
early while continuing independent analysis. A local Markdown report, an existing issue, a document
provider or chat may be used when that is the agreed destination; analysis methodology is unchanged.

The plugin does not bundle document connectors, `$lark-doc` or `$artifact-boundary-review`. Check the
available skills/tools before invoking them. For Lark, use the available Lark document skill and its
document tools/CLI under the authorized user identity. For another destination, use its available
purpose-built capability. Do not assume a particular command is installed or switch accounts to write.

If the agreed destination or verification is unavailable, complete the analysis and retain a local
draft where allowed. State the precise delivery gap and ask before changing the deliverable. A draft
or chat summary is not a verified external report. Missing an optional review skill does not block the
report: perform the same audience/scope/final-state review directly unless repository policy requires
that specific skill, in which case report the unavailable required step.

## Write And Verify One Report

Lead with the decision and scope. Retain freshness, sources, definitions, data coverage, evidence,
confidence and actions with outcome criteria. Full reviews include every required baseline row;
focused reports contain what answers the question. Use exact tables for comparisons and charts where
trends matter. Do not reproduce raw private data that the decision does not need.

Reuse a requested existing report/outcome record; otherwise a newly requested analysis may have its own
report. Rendering corrections update the same artifact. Apply available artifact-boundary review in
the final pass, or directly check reader/use, accurate conclusions and current authorized scope.

Fetch the saved document/file and verify actual content and structure. Use provider rendering/preview
when visual formatting matters. Correct and recheck affected content; reuse the verified state if no
further changes occurred. Report the conclusion and verified artifact link, or clearly state the gap.
Do not send the report to others or alter source-system settings without corresponding authorization.
